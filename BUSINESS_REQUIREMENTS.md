# Бизнес-требования к приложению-конвертеру веб-страниц

## 1. Назначение документа

Документ определяет бизнес-требования к серверному Spring Boot приложению, которое по запросу получает веб-страницу по URL и возвращает её представление в одном из трёх форматов: MHTML, PDF или PPTX.

Требования предназначены для согласования ожидаемого поведения продукта, последующего проектирования, разработки, тестирования и приёмки. Конкретная внутренняя архитектура и детали реализации в область документа не входят.

## 2. Бизнес-цель

Предоставить клиентским системам единый программный интерфейс для автоматизированного сохранения динамических веб-страниц в переносимые файловые форматы:

- **MHTML** — архивное представление страницы и связанных ресурсов;
- **PDF** — документ для просмотра, печати и передачи;
- **PPTX** — презентация, содержащая визуальное представление страницы.

Решение должно обеспечивать воспроизводимый результат, учитывать динамически загружаемый контент и диаграммы ECharts, безопасно обрабатывать внешние URL и поставляться как автономно запускаемый исполняемый JAR.

## 3. Область решения

### 3.1. Входит в область

- запуск приложения как исполняемого JAR;
- конфигурация HTTP-порта параметром запуска;
- три POST API: `MakeMHTML`, `MakePDF`, `MakePPTX`;
- приём URL целевой страницы в JSON;
- загрузка и ожидание готовности динамической страницы;
- формирование и возврат MHTML, PDF или PPTX;
- валидация входных данных и политика безопасного доступа к URL;
- обработка ошибок, журналирование и эксплуатационная наблюдаемость;
- конфигурируемые таймауты, лимиты и параллельность.

### 3.2. Не входит в область

- хранение сформированных файлов после завершения запроса;
- пользовательский веб-интерфейс;
- редактирование полученных документов;
- пакетная конвертация нескольких URL одним запросом;
- планировщик конвертаций;
- обязательная поддержка страниц, требующих интерактивной аутентификации, CAPTCHA, ручного подтверждения или установки браузерных расширений;
- обход ограничений, установленных владельцем целевого ресурса;
- реализация самого приложения в рамках настоящего документа.

## 4. Термины и акторы

### 4.1. Термины

- **Клиент** — информационная система или пользовательский программный компонент, вызывающий API конвертера.
- **Целевая страница** — веб-страница, заданная URL в запросе.
- **Динамическая страница** — страница, содержимое которой изменяется после первоначальной загрузки за счёт JavaScript, сетевых запросов или отложенного рендеринга.
- **Готовность страницы** — состояние, при котором выполнены установленные критерии завершения загрузки и стабилизации отображения.
- **ECharts** — визуализации, построенные библиотекой Apache ECharts и отрисованные на странице в Canvas или SVG.
- **Конвертация** — загрузка целевой страницы и создание результирующего файла выбранного формата.
- **SSRF** — атака, при которой сервер принуждается выполнять нежелательные запросы к внутренним, локальным или служебным ресурсам.
- **MHTML** — MIME-архив веб-страницы и доступных связанных ресурсов.
- **PPTX** — презентация формата Office Open XML.

### 4.2. Акторы

- **Система-клиент** — отправляет запрос на конвертацию и получает файл либо структурированную ошибку.
- **Оператор** — запускает и конфигурирует приложение, контролирует его состояние и журналы.
- **Администратор безопасности** — задаёт допустимую политику сетевого доступа и ограничения URL.
- **Владелец целевого ресурса** — определяет доступность, содержимое и правила использования страницы; не управляется приложением.

## 5. Пользовательские сценарии

### 5.1. Создание MHTML

1. Клиент отправляет POST-запрос в `MakeMHTML` с URL страницы.
2. Приложение проверяет JSON и URL, включая сетевые ограничения.
3. Приложение загружает страницу, ожидает её готовности и отрисовки динамического содержимого.
4. Приложение формирует MHTML-архив.
5. Клиент получает файл MHTML с корректными HTTP-заголовками либо описание ошибки.

### 5.2. Создание PDF

1. Клиент отправляет POST-запрос в `MakePDF` с URL страницы.
2. Приложение выполняет валидацию и безопасную загрузку страницы.
3. После готовности страницы приложение формирует PDF, отражающий итоговый визуальный вид.
4. Клиент получает PDF-файл либо описание ошибки.

### 5.3. Создание PPTX

1. Клиент отправляет POST-запрос в `MakePPTX` с URL страницы.
2. Приложение выполняет валидацию и безопасную загрузку страницы.
3. После готовности страницы приложение создаёт PPTX с визуальным представлением страницы.
4. Клиент получает презентацию либо описание ошибки.

### 5.4. Отклонение небезопасного или некорректного URL

1. Клиент передаёт пустой, синтаксически некорректный, запрещённый либо недопустимый политикой URL.
2. Приложение не загружает ресурс.
3. Клиент получает структурированную ошибку с подходящим HTTP-кодом без раскрытия чувствительных сведений.

### 5.5. Ошибка или превышение времени ожидания

1. Целевая страница недоступна, не завершает загрузку либо не достигает критериев готовности в пределах настроенного времени.
2. Приложение прекращает обработку, освобождает ресурсы и возвращает структурированную ошибку.
3. В журнале фиксируются безопасные диагностические данные и идентификатор запроса.

## 6. Функциональные требования

### 6.1. Общие требования

- **FR-001.** Приложение должно предоставлять три операции конвертации через HTTP POST: `MakeMHTML`, `MakePDF`, `MakePPTX`.
- **FR-002.** Каждая операция должна принимать JSON-объект с одним обязательным бизнес-параметром `url`.
- **FR-003.** Каждая успешная операция должна возвращать бинарное содержимое файла непосредственно в теле HTTP-ответа.
- **FR-004.** Формат результата должен однозначно определяться вызванной операцией; клиент не должен передавать формат отдельно.
- **FR-005.** Каждый запрос должен иметь или получать уникальный идентификатор корреляции, доступный в заголовке ответа и безопасных диагностических сообщениях.
- **FR-006.** После завершения запроса приложение должно освобождать временные файлы, браузерные сессии, процессы и иные выделенные ресурсы.
- **FR-007.** Частичный или повреждённый файл не должен возвращаться как успешный результат.
- **FR-008.** Поведение при перенаправлениях должно подчиняться той же валидации безопасности, что и исходный URL: каждый конечный адрес и переход должны проверяться до доступа.

### 6.2. Валидация URL

- **FR-009.** Поле `url` обязательно, должно быть строкой, не быть пустым и представлять абсолютный URL.
- **FR-010.** Разрешёнными схемами должны быть только `http` и `https`, если более строгая политика не задана конфигурацией.
- **FR-011.** URL со схемами `file`, `data`, `javascript` должны безусловно отклоняться до попытки загрузки.
- **FR-012.** URL не должен содержать учётные данные в authority-компоненте (`user:password@host`).
- **FR-013.** Приложение должно проверять имя хоста, результат DNS-разрешения и фактический адрес соединения, чтобы предотвращать доступ к loopback, link-local, private, multicast, unspecified, служебным адресам облачных metadata-сервисов и иным запрещённым сетям.
- **FR-014.** Политика разрешённых и запрещённых доменов/сетей должна быть конфигурируемой оператором; запреты безопасности должны иметь приоритет над разрешениями общего характера.
- **FR-015.** Защита должна учитывать DNS rebinding, альтернативные формы записи IP-адресов, IPv4/IPv6, перенаправления и URL-нормализацию.
- **FR-016.** Длина URL и размер входного JSON должны ограничиваться конфигурацией.

### 6.3. Загрузка динамической страницы

- **FR-017.** Страница должна загружаться в браузерной среде с выполнением JavaScript.
- **FR-018.** До создания файла приложение должно дождаться как минимум завершения базовой загрузки документа и применить конфигурируемый критерий стабилизации динамического содержимого.
- **FR-019.** Критерий готовности должен поддерживать ожидание отсутствия активной сетевой нагрузки в течение настраиваемого периода и/или достижение настраиваемого максимального времени ожидания.
- **FR-020.** Должна быть предусмотрена возможность настроить дополнительную задержку после базовой готовности страницы для завершения анимаций, шрифтов, изображений и отложенного рендеринга.
- **FR-021.** Приложение должно дождаться завершения отрисовки доступных экземпляров ECharts и зафиксировать их итоговое визуальное состояние.
- **FR-022.** ECharts, отрисованные через Canvas или SVG, должны присутствовать в визуальных результатах PDF и PPTX; в MHTML они должны сохраняться настолько полно, насколько это допускают формат и браузерный механизм архивации.
- **FR-023.** Бесконечные сетевые соединения, периодические запросы и непрерывные анимации не должны приводить к бесконечному ожиданию.
- **FR-024.** По достижении настроенного таймаута приложение должно завершить операцию контролируемой ошибкой, а не формировать заведомо неполный результат, если иной режим явно не согласован.

### 6.4. Требования к MHTML

- **FR-025.** Результат должен быть корректным MIME-архивом веб-страницы с расширением `.mhtml`.
- **FR-026.** Архив должен включать итоговый HTML и доступные связанные ресурсы, необходимые для максимально полного автономного просмотра.
- **FR-027.** Приложение должно сохранять кодировку текста и корректно представлять не-ASCII символы.
- **FR-028.** Недоступные или запрещённые ресурсы не должны подменяться данными из небезопасных источников; существенная невозможность создать пригодный архив должна приводить к ошибке.
- **FR-029.** Не гарантируется полная автономная работоспособность интерактивной логики страницы после открытия MHTML; ожидается архивное визуальное представление в пределах возможностей формата.

### 6.5. Требования к PDF

- **FR-030.** Результат должен быть валидным PDF-файлом с расширением `.pdf` и открываться стандартными средствами просмотра PDF.
- **FR-031.** PDF должен отражать итоговое визуальное состояние страницы после выполнения критериев готовности, включая видимые ECharts.
- **FR-032.** Фоновые изображения и цвета, необходимые для сохранения визуального смысла страницы, должны включаться в результат.
- **FR-033.** Правила размера страницы, ориентации, полей, масштаба и использования экранных либо печатных стилей должны быть явно определены конфигурацией или дальнейшим решением по открытым вопросам.
- **FR-034.** Длинная страница должна быть представлена без потери содержимого в пределах выбранной стратегии разбиения на страницы.

### 6.6. Требования к PPTX

- **FR-035.** Результат должен быть валидным PPTX-файлом с расширением `.pptx` и открываться совместимыми приложениями для презентаций.
- **FR-036.** PPTX должен содержать визуальное представление итогового состояния страницы, включая видимые ECharts.
- **FR-037.** Базовый допустимый способ представления — одно или несколько растровых/векторных изображений страницы, размещённых на слайдах без искажения пропорций.
- **FR-038.** Стратегия разбиения длинной страницы на слайды, формат слайда и разрешение визуального представления должны быть конфигурируемыми либо согласованными до реализации.
- **FR-039.** На стыках слайдов не должно быть непреднамеренных пропусков или дублирования существенного содержимого.
- **FR-040.** Требование редактируемости отдельных DOM-элементов и диаграмм в PPTX не устанавливается, если оно не будет принято отдельным решением.

## 7. API-контракты бизнес-уровня

> Точные базовый путь и регистр маршрутов должны быть закреплены до разработки. В настоящем документе используются маршруты `/MakeMHTML`, `/MakePDF`, `/MakePPTX`, соответствующие заданным именам операций.

### 7.1. Общий формат запроса

**HTTP-метод:** `POST`  
**Content-Type запроса:** `application/json`  
**Тело:**

```json
{
  "url": "https://example.org/report?id=123"
}
```

Неизвестные поля должны либо отклоняться как ошибка запроса, либо игнорироваться единообразно для всех операций; политика требует окончательного решения.

### 7.2. MakeMHTML

**Маршрут:** `POST /MakeMHTML`

Пример успешного ответа:

```http
HTTP/1.1 200 OK
Content-Type: multipart/related
Content-Disposition: attachment; filename="example.org-20260928T000000Z.mhtml"; filename*=UTF-8''example.org-20260928T000000Z.mhtml
X-Correlation-ID: 4ad7d9f0-...

<бинарное содержимое MHTML>
```

Если фактическая реализация формирует MHTML с более точным зарегистрированным MIME-типом, он может быть выбран по результатам технической проверки совместимости; тип должен быть документирован и использоваться единообразно.

### 7.3. MakePDF

**Маршрут:** `POST /MakePDF`

Пример успешного ответа:

```http
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="example.org-20260928T000000Z.pdf"; filename*=UTF-8''example.org-20260928T000000Z.pdf
X-Correlation-ID: 4ad7d9f0-...

<бинарное содержимое PDF>
```

### 7.4. MakePPTX

**Маршрут:** `POST /MakePPTX`

Пример успешного ответа:

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.openxmlformats-officedocument.presentationml.presentation
Content-Disposition: attachment; filename="example.org-20260928T000000Z.pptx"; filename*=UTF-8''example.org-20260928T000000Z.pptx
X-Correlation-ID: 4ad7d9f0-...

<бинарное содержимое PPTX>
```

### 7.5. Формат ошибки

Ошибки должны возвращаться в JSON и не маскироваться под файл:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
X-Correlation-ID: 4ad7d9f0-...
```

```json
{
  "type": "about:blank",
  "title": "Не удалось преобразовать страницу",
  "status": 422,
  "code": "PAGE_RENDER_FAILED",
  "detail": "Страница не достигла состояния готовности",
  "correlationId": "4ad7d9f0-..."
}
```

Поле `detail` должно быть безопасным для клиента и не содержать внутренних путей, стеков, секретов, полного URL с query-параметрами или фрагментом.

### 7.6. Правила именования файлов

- Имя должно формироваться сервером и передаваться через `Content-Disposition: attachment`.
- Рекомендуемый шаблон: `<безопасный-host>-<UTC timestamp>.<расширение>`.
- Имя должно быть очищено от управляющих символов, разделителей путей и символов, способных нарушить HTTP-заголовки или файловую систему.
- Параметр `filename` должен содержать безопасный ASCII-вариант, а `filename*` — UTF-8-вариант согласно применимому стандарту.
- Query-параметры, фрагмент, пользовательские данные и секреты из URL не должны попадать в имя файла.
- Для MHTML используется `.mhtml`, для PDF — `.pdf`, для PPTX — `.pptx`.

## 8. Ошибки и HTTP-коды

| Ситуация | HTTP-код | Пример бизнес-кода |
|---|---:|---|
| Успешная конвертация | `200` | — |
| Некорректный JSON, отсутствующий/пустой `url`, неверный тип | `400` | `INVALID_REQUEST` |
| Недопустимая схема или синтаксически некорректный URL | `400` | `INVALID_URL` |
| URL запрещён политикой безопасности, включая SSRF-ограничения | `403` | `URL_NOT_ALLOWED` |
| Целевая страница не найдена | `404` | `TARGET_NOT_FOUND` |
| Целевой ресурс требует недоступной аутентификации | `422` | `TARGET_AUTH_REQUIRED` |
| Страница загружена, но не может быть корректно обработана/преобразована | `422` | `PAGE_RENDER_FAILED` / `CONVERSION_FAILED` |
| Превышен настроенный таймаут обработки | `504` | `CONVERSION_TIMEOUT` |
| Исчерпан настроенный лимит параллельных операций | `429` или `503` согласно принятой политике | `CAPACITY_EXCEEDED` |
| Внутренняя непредвиденная ошибка | `500` | `INTERNAL_ERROR` |
| Временная недоступность зависимого компонента | `503` | `SERVICE_UNAVAILABLE` |

Дополнительные требования:

- ответ об ошибке должен иметь `Content-Type: application/problem+json`;
- один и тот же класс ошибки должен обрабатываться одинаково во всех трёх API;
- ошибки целевого HTTP-сервера должны преобразовываться в стабильную модель ошибок приложения, а не безусловно передаваться клиенту;
- клиенту нельзя возвращать stack trace, локальные пути, внутренние IP-адреса, содержимое секретных заголовков или подробности сетевой инфраструктуры;
- при `429` следует поддержать заголовок `Retry-After`, если приложение может корректно определить рекомендуемое время повтора.

## 9. Конфигурация и запуск

- **NFR-001.** Приложение должно поставляться как исполняемый JAR и запускаться стандартной командой Java, например:

  ```bash
  java -jar converter.jar --server.port=8080
  ```

  Значение `8080` является только примером, а не обязательным портом.

- **NFR-002.** HTTP-порт должен задаваться параметром запуска Spring Boot `--server.port=<port>`; допускаются также стандартные механизмы внешней конфигурации Spring Boot при сохранении предсказуемого приоритета настроек.
- **NFR-003.** Некорректное или занятое значение порта должно приводить к явной ошибке запуска.
- **NFR-004.** Без изменения кода должны конфигурироваться: таймауты загрузки и конвертации, критерии ожидания, дополнительная задержка, лимит параллельных операций, размер очереди, лимиты входа/выхода, сетевые allowlist/denylist, временный каталог и параметры браузерной среды.
- **NFR-005.** Значения конфигурации и их единицы измерения должны быть документированы; секреты не должны храниться в исходном коде или попадать в журнал.

## 10. Безопасность и защита данных

### 10.1. SSRF и сетевой доступ

- Приложение должно использовать принцип запрета по умолчанию для явно опасных адресов и схем.
- Доступ к localhost, loopback, link-local, private/internal сетям, UNIX/file-ресурсам, metadata endpoints и административным интерфейсам должен блокироваться, если отдельная доверенная конфигурация не задаёт более узкое контролируемое исключение.
- Проверка должна выполняться до соединения и повторяться для перенаправлений и подресурсов страницы, насколько это технически возможно.
- DNS-ответы должны проверяться на запрещённые IP-диапазоны; приложение не должно доверять только строковому имени хоста.
- Исходящие запросы браузера к подресурсам также должны подчиняться политике сетевого доступа.
- Приложение не должно автоматически передавать целевому ресурсу входящие клиентские заголовки `Authorization`, `Cookie`, прокси-учётные данные или иные секреты.

### 10.2. Защита клиентских данных

- URL и содержимое страниц должны обрабатываться только для выполнения запроса и не сохраняться дольше необходимого без отдельного согласованного требования.
- Временные файлы должны создаваться с ограниченным доступом и удаляться после успеха, ошибки или прерывания обработки.
- Параллельные запросы должны быть изолированы: данные и браузерный контекст одного клиента не должны быть доступны другому.
- Кэш, cookies, local storage и иные данные браузерной сессии не должны переиспользоваться между независимыми запросами, если безопасный режим общего доступа не определён отдельно.
- Соединение клиента с приложением должно поддерживать размещение за TLS-терминатором; необходимость встроенного TLS определяется средой эксплуатации.
- Доступ к API должен ограничиваться средствами среды размещения и/или механизмом аутентификации, выбранным до промышленной эксплуатации.
- Полученные файлы не должны включать диагностические данные приложения, внутренние заголовки или сведения других запросов.

## 11. Логирование, аудит и наблюдаемость

- Для каждого запроса должны журналироваться: идентификатор корреляции, операция, время начала и завершения, результат, категория ошибки и длительность.
- Полный URL журналировать запрещено. Допустим безопасно нормализованный источник, например схема и host, если это разрешено политикой данных.
- Query-параметры и fragment URL не должны попадать в журналы, метрики, трассировки и тексты исключений, доступные оператору без специального защищённого режима.
- Значения заголовков авторизации, cookies, токены, ключи, пароли и иные секреты не должны журналироваться.
- Тела входных запросов, содержимое страниц и сформированные файлы не должны журналироваться.
- Уровни журналирования должны быть конфигурируемыми; расширенная диагностика не должна отключать маскирование секретов.
- Приложение должно предоставлять стандартные средства проверки работоспособности и готовности, не инициирующие конвертацию и не раскрывающие чувствительные сведения.
- Следует предоставлять метрики количества операций, длительности, ошибок, таймаутов, текущей занятости и очереди без высококардинальных меток с URL.

## 12. Производительность, таймауты и параллельность

- Таймаут полной операции, таймаут навигации, ожидание готовности и дополнительная задержка должны быть конфигурируемыми и иметь безопасные значения по умолчанию, определяемые на этапе проектирования и нагрузочного тестирования.
- Максимальное число одновременно выполняемых конвертаций должно быть конфигурируемым с учётом CPU, памяти и стоимости браузерных процессов.
- Размер очереди ожидающих запросов и поведение при её заполнении должны быть конфигурируемыми и документированными.
- Максимальный размер результата, потребление временного диска и доступная память должны контролироваться; при превышении лимита операция должна завершаться контролируемой ошибкой.
- Приложение должно предотвращать неограниченное создание браузерных процессов и накопление зависших задач.
- Отмена клиентского запроса должна, насколько возможно, прекращать связанную обработку и освобождать ресурсы.
- Конкретные численные SLA, таймауты, лимиты размеров и параллельность не фиксируются настоящим документом и должны определяться на основании целевой инфраструктуры и нагрузочных испытаний.
- Повтор запросов приложением не должен выполняться автоматически, если это может увеличить нагрузку или изменить визуальное состояние; политика повторов требует отдельного решения.

## 13. Эксплуатационные требования

- Приложение должно запускаться в поддерживаемой среде Java, версия которой фиксируется проектом до реализации.
- Зависимость от установленного браузера и требования к его версии должны быть явно документированы и проверяться при запуске или диагностике.
- Ошибка запуска браузерного компонента должна обнаруживаться до или при первом запросе с понятным сообщением оператору.
- Завершение приложения должно корректно прекращать приём новых запросов, завершать или отменять активные операции по принятой политике и освобождать дочерние процессы.
- Временное хранилище должно быть контролируемым, очищаемым и пригодным для мониторинга свободного места.
- Сборка должна быть воспроизводимой; версии зависимостей должны быть зафиксированы средствами сборки.
- Должны быть документированы параметры запуска, конфигурация, коды ошибок, требования к Chromium, проверка работоспособности и типовые действия при сбоях.
- Развёртывание не должно требовать обязательных платных сервисов или библиотек.

## 14. Ограничения и допущения

- Целевая страница доступна приложению по сети и её использование для конвертации разрешено владельцем/клиентом.
- Качество результата зависит от поведения страницы, доступности её ресурсов, шрифтов, политик CORS/CSP, антибот-защиты и возможностей браузерного движка.
- Страницы с CAPTCHA, DRM, аппаратно защищённым контентом или обязательным ручным взаимодействием могут не поддерживаться.
- Аутентифицированные страницы не считаются поддержанными до определения безопасного механизма передачи и изоляции учётных данных.
- MHTML может по-разному открываться в разных программах; эталонный просмотрщик должен быть согласован.
- PDF и PPTX фиксируют визуальное состояние страницы и не обязаны сохранять исходную интерактивность.
- Для ECharts ожидается фиксация уже отрисованной визуализации; извлечение исходных данных или построение редактируемой диаграммы не требуется.
- Приложение не гарантирует идентичность результата во всех версиях браузера, операционных системах и наборах шрифтов; эталонная среда должна быть зафиксирована.

## 15. Необязательные технологические ограничения и рекомендации

Этот раздел не является предписанием реализации и не делает перечисленные компоненты обязательными. При выборе технологий следует отдавать предпочтение бесплатным, поддерживаемым и совместимым по лицензиям решениям; платные зависимости не должны быть обязательным условием работы приложения.

Рекомендуемые бесплатные компоненты для оценки:

- **Selenium** — управление браузером и ожидание состояния динамической страницы;
- **Chromium** — браузерный движок для выполнения JavaScript, визуального рендеринга, формирования PDF и, при подтверждённой поддержке, MHTML;
- **Apache POI** — создание PPTX;
- **Apache Batik** — обработка SVG, в том числе при подготовке визуализаций для PPTX.

Окончательный выбор должен учитывать лицензии, поддержку требуемых функций, безопасность, совместимость версий и воспроизводимость результата.

## 16. Критерии приёмки

1. Исполняемый JAR успешно запускается на указанном корректном порту через параметр `--server.port` и принимает HTTP-запросы на этом порту.
2. Каждая из трёх операций принимает корректный JSON с публичным разрешённым HTTP/HTTPS URL и при успехе возвращает файл заявленного формата.
3. Ответы имеют корректные `Content-Type`, `Content-Disposition`, расширение имени файла и идентификатор корреляции.
4. Возвращённые MHTML, PDF и PPTX проходят проверку целостности и открываются согласованными эталонными программами.
5. Тестовая динамическая страница, содержимое которой появляется после первоначальной загрузки, отражается в каждом результирующем формате в пределах требований к нему.
6. Видимая тестовая диаграмма ECharts присутствует в PDF и PPTX; для MHTML подтверждён согласованный уровень сохранения в эталонном просмотрщике.
7. Пустой URL, неверный JSON и синтаксически некорректный URL отклоняются без запуска загрузки и возвращают согласованные ошибки.
8. URL со схемами `file`, `data`, `javascript` отклоняются.
9. Попытки доступа к loopback, private/link-local адресам, локальным файлам, metadata endpoints и запрещённым адресам через перенаправление или DNS не приводят к сетевому доступу к ним.
10. Подресурсы страницы не позволяют обойти установленную сетевую политику.
11. При недостижении готовности страницы операция завершается по настроенному таймауту, возвращает структурированную ошибку и освобождает ресурсы.
12. При превышении настроенной ёмкости приложение предсказуемо отклоняет или ставит запросы в очередь согласно конфигурации и не создаёт неограниченное число процессов.
13. Журналы и метрики не содержат query-параметров URL, fragment, токенов, cookies, секретных заголовков, тел страниц и содержимого файлов.
14. Временные данные удаляются после успешных и ошибочных операций; браузерные контексты разных запросов изолированы.
15. Все классы ошибок из согласованной модели возвращаются единообразно для трёх API и не раскрывают внутренние детали.
16. Документация эксплуатации описывает запуск, конфигурацию, ограничения, health/readiness-проверки и диагностику типовых сбоев.
